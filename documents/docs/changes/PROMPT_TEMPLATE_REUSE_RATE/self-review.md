## 1. Implementation Summary

Implemented Prompt Template Reuse Rate end-to-end per `impl-plan.md`: (1) BE write path — `V510__add_template_usage_tracking.sql` adds `tbl_fact_template_usage_stat` plus 3 `tbl_dim_artifact_type` seed rows; `GithubWebhookService.handlePullRequest` gained a validation loop (`validateTemplateUsage`/`fetchTemplateUsageBlob` and two small private helpers) that resolves each changed file's phase/template via the existing DB-driven `ArtifactTypeScope` mapping, compares header structure (title+level, not body) between the changed file and its template, and records the result through a new `TemplateUsageStatPort` → `TemplateUsageStatJdbcAdapter` upsert, invoked via a `TemplateUsageStatWriter` `REQUIRES_NEW` bean (mirrors `AdminAuditLogWriter`) so a counter-write failure never rolls back or blocks the webhook response. (2) BE read path — `PmDashboardRepositoryPort.findTemplateUsage` / `PmDashboardJdbcAdapter` implementation, `PmDashboardService.getTemplateUsage` (reuses existing `requirePm` for PM/ADMIN authorization, computes `usageRate` with the OI-10 rounding rule), `PmDashboardController` `GET /api/v1/pm/dashboard/template-usage`, and `PmDashboardDtos.TemplateUsageDto`. (3) FE — `endpoints.pmDashboard.templateUsage(...)` in `api.ts` (sibling namespace, per spec-pack.md over this session's own earlier inference), `formatUsageRate` in `utils.ts`, new `TemplateUsageByPhase.tsx` table component mounted in `PMDashboardPage.tsx` immediately after `AllTicketsTable`, gated on a `["pm-dashboard", "template-usage", ...]` `useQuery` enabled only when both `projectId`/`repositoryId` are selected.

No deviation from `impl-plan.md`'s chosen alternatives (ID-1(a), ID-2(a), ID-3). One scope boundary remains recorded rather than silently worked around — see §8: the webhook-redelivery double-counting risk flagged in `review-checklist.md` §7 was confirmed present (no dedupe key found) and is not fixed in this ticket.

**Phase 5 revision round 1 (2026-08-11):** Human review rejected the first implementation pass with 4 findings (table style inconsistent with `AllTicketsTable`; `findTemplateUsage` returning phases outside the feature's scope; missing i18n for the new section title/description; missing i18n + unwanted uppercase transform on table headers). All 4 were classified, fixed, and re-verified — see §7 (Bugs Found) and §11 (Items reviewed by humans) for full detail. Fixes: `TemplateUsageByPhase.tsx` rewritten to use the shared `CDataTable` component (basic/non-paginated mode) instead of a hand-rolled `<table>`; `PmDashboardJdbcAdapter.findTemplateUsage` now scopes its query with a data-driven `WHERE EXISTS (... tbl_dim_artifact_type ...)` clause (Business Rule #7-compliant, no hard-coded phase list); `en`/`vi`/`ja` locale keys added for all new UI text. `spec-pack.md` and `open-issues.md` updated with `OI-11`/`OI-12` and a new Business Rule #9 (i18n requirement for new UI text) to close the gaps these findings exposed.

**Phase 5 revision round 2 (2026-08-11):** Human review rejected the round-1 fix diff with 2 further findings: (a) the round-1 `WHERE EXISTS (... tbl_dim_artifact_type ...)` filter still let phase `0-A` leak into `findTemplateUsage`'s response, because that table is shared with an unrelated feature (AI-safety file scanning) that maps 3 artifact types to `0-A`; (b) `validateTemplateUsage(...)` ran on every supported `pull_request` webhook action (`opened`/`synchronize`/`reopened`/`closed`) instead of only once per PR, duplicating/inflating `total_check_count`/`template_match_count` since each delivery re-scans the PR's full cumulative diff through a purely additive counter. Both findings were classified as Blocker, a fix plan was drafted with 2 open implementation-approach decisions, and both decisions were confirmed with the human reviewer before any code was changed (see §11). Fixes: `findTemplateUsage`'s filter replaced with a literal `WHERE ph.phase_code IN ('1','2','3','4','5','6','7','8')`, grounded directly in the already-fixed Terminology phase scope rather than the indirect, cross-feature `tbl_dim_artifact_type` proxy; `GithubWebhookService.handlePullRequest` now gates the `validateTemplateUsage(...)` call on `"closed".equals(action) && pullRequest.path("merged").asBoolean(false)`. `spec-pack.md` and `open-issues.md` updated with `OI-13`/`OI-14`, a corrected OI-11 status, a clarified Business Rule #7, and a new Business Rule #11 (once-per-PR recording condition).

**Phase 5 revision round 3 (2026-08-17):** Codex automated review (`codex-review.md`, verdict `NEEDS_FIX`) raised 3 findings plus a set of missed tests and 2 open design questions. Both open questions were put to the ticket owner before any code was changed (see §11): (1) whether to add webhook-redelivery dedup — declined, accepted as risk; (2) whether the shared, PR-level `resolveRevision`/`listTree` fetch errors should be classified the same way as the existing per-file blob-fetch errors — confirmed yes. Fixes: `resolveRevision`/`listTree`'s catch block now reuses the existing `isSkippableFetchError` classification (401/403/404 skip, other errors propagate) instead of swallowing every error; the `templateUsageStatWriter.recordIndependently(...)` call site is now wrapped in `try/catch (DataAccessException)` so a counter-write failure for one file is logged and skipped rather than aborting the webhook, restoring the Best-Effort Audit/Stat Write Pattern the code was supposed to follow; `PMDashboardPage.tsx`/`TemplateUsageByPhase.tsx` now thread `templateUsageQuery.isLoading` through so the empty-state message no longer flashes while the query is still in flight. `spec-pack.md` and `open-issues.md` updated with `OI-15` (Accepted Risk), `OI-16`/`OI-17` (Resolved), and annotations scoping the "exactly once per PR" guarantee and the skippable-fetch business rule.
