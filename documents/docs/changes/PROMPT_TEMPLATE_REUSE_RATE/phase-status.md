## Open Issues

One new Open Issue was raised and resolved during Phase 3 review: **OI-10** — `usageRate` rounding rule was unspecified in `spec-pack.md` (risk of inconsistent display precision, e.g. `66.6666666667%` vs `67%`). Resolved: round to exactly 1 decimal place server-side, `null` when `totalCheckCount == 0`, FE appends `%` without re-rounding. Baked into `spec-pack.md` (Terminology, §6.3 Output, AC-8), `open-issues.md`, `impact-analysis.md`, and `impl-plan.md`. (Note: OI-10 had been decided but was found — during the Phase 5 round-1 revision — to have never actually been recorded in `spec-pack.md` §18's Open Issues table; that gap was retroactively closed alongside OI-11/OI-12 below.)

Two new Open Issues were raised during the Phase 5 human review round 1 (2026-08-11) and resolved in that revision:

- **OI-11** — Shipped `findTemplateUsage` had no phase filter, so the response included phases with no mapped artifact type (`0-A`, `0-B`, `9`, `10`), contradicting spec-pack's own Terminology/Boundary Values (8 in-scope phases). Resolved (initially): data-driven `WHERE EXISTS (... tbl_dim_artifact_type ...)` filter, no hard-coded phase-code list, per Business Rule #7. **Later superseded by OI-13** — see below.
- **OI-12** — Shipped `TemplateUsageByPhase.tsx` UI text (section title/description, table headers) had no locale keys in `en`/`vi`/`ja`, only hard-coded English `defaultValue` fallbacks. Resolved: real keys added to all 3 locale files; new Business Rule #9 in `spec-pack.md` mandates this for future UI text.

Two further new Open Issues were raised during the Phase 5 human review round 2 (2026-08-11) and resolved in this turn's revision:

- **OI-13** — OI-11's `EXISTS`/JOIN fix was insufficient: phase `0-A` carries 3 `tbl_dim_artifact_type` rows for an unrelated feature (AI-safety file scanning), so it still passed the filter and leaked into the response. Resolved: literal `WHERE ph.phase_code IN ('1','2','3','4','5','6','7','8')`, grounded directly in the Terminology-defined phase scope rather than an indirect, cross-feature proxy table.
- **OI-14** — `validateTemplateUsage(...)` ran unconditionally on every supported `pull_request` webhook action, so a PR's `opened`/`synchronize`/`closed` deliveries each independently re-scanned the same cumulative diff through a purely additive counter, duplicating/inflating `total_check_count`/`template_match_count`. Resolved: gated the call on `action=="closed" && merged==true`, per new Business Rule #11.

Three further new Open Issues raised during Phase 5 Codex automated review round 3 (2026-08-17):

- **OI-15** — GitHub webhook redelivery of the same `closed`+`merged` event (at-least-once transport, no dedupe key stored anywhere) could double-count `total_check_count`/`template_match_count`. Ticket owner explicitly declined a fix: no dedup/idempotency mechanism exists anywhere else in the codebase for GitHub webhook redelivery, so adding one solely for this feature was judged unwarranted. Status: **Accepted Risk** (not Resolved) — no code change; ratified explicitly by the ticket owner.
- **OI-16** — The shared `resolveRevision`/`listTree` calls in `validateTemplateUsage` caught `Exception` generically and swallowed even non-HTTP/5xx failures, silently skipping validation and returning a false-success webhook response. Resolved: reused the existing `isSkippableFetchError` classification (401/403/404 → skip, else → propagate) already applied to per-file blob fetches.
- **OI-17** — `templateUsageStatWriter.recordIndependently(...)` had no try/catch at its `GithubWebhookService` call site, so a `DataAccessException` (e.g. transient DB outage) during counter-write would abort the entire webhook, violating the spec's own Best-Effort Audit/Stat Write Pattern. Resolved: wrapped the call site in `try/catch (DataAccessException)`, logging a warning and continuing to the next file.

All OI-1..14 in `open-issues.md` are now Resolved (OI-11 marked Superseded by OI-13, its replacement). Two implementation-shape decisions were resolved directly in `impl-plan.md` (not escalated to `open-issues.md`, per the reasoning in `impl-plan.md` §14):

1. Where the new per-file validation logic lives, given `ticketKeyFromPath`/`isSkippableBlobError` are `private` and not callable across class boundaries — resolved: implement locally inside `GithubWebhookService` (ID-1(a)).
2. Where the write-side counter upsert lives relative to the existing PM-dashboard read port — resolved: new dedicated `TemplateUsageStatPort` (write), existing `PmDashboardRepositoryPort` gains only a new read method (ID-2(a)).

A pre-existing doc-vs-source discrepancy was also newly noted (not raised as an Open Issue, out of this ticket's scope): `CLAUDE.md` claims hexagonal layering is "enforced by ArchUnit," but no `ArchitectureTest.java` or any `@AnalyzeClasses`/`ArchRule` usage was found under `src/test` — recorded in `impact-analysis.md` §14/§17 as a manual-review-only risk for this ticket.
